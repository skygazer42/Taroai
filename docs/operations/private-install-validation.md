# Private Install Validation

This runbook defines the operator-facing validation report for BYOC, VPC, private, and air-gapped installs. It is a contract for install readiness reporting; the executable helper is `scripts/validate-install.sh`.

## Required Checks

Every `InstallValidationReport` must include these checks:

- release package integrity: the release zip can be verified with the packaged
  manifest, schema, checksums, required files, optional expected package SHA256
  from transfer evidence, optional detached Ed25519 release signature, and
  content scanning for secret-shaped tokens, private key blocks, and
  credentialed HTTP URLs. The package builder and verifier also reject local
  workspace residue such as `.env` variants, editor backups, swap files,
  temporary files, OS metadata, IDE settings, coverage reports, credential-named
  files such as `.netrc`, `.npmrc`, `.pypirc`, kubeconfigs, SSH identity names,
  cloud credential directories, service-account JSON names, and
  certificate/private-key/key-store suffixes, nested archives, virtualenv
  directories, cache directories, and previous release outputs.
  Cloud, production, and customer-operated installs must provide
  `--release-package` or release transfer evidence that resolves to the verified
  package.
- database migration: a migration plan JSON generated by
  `python -m taroai.db.migration_cli` reports no pending migrations and no
  unknown applied migrations after the package migration job has run.
  Cloud, production, and customer-operated installs must provide
  `--migration-plan`.
- Redis connectivity: Redis ping succeeds and the configured worker queue
  database is reachable. Cloud, production, and customer-operated installs must
  provide `--redis-queue-verification`.
- object storage read/write: the configured bucket accepts upload, download,
  and delete through the object storage adapter. Cloud, production, and
  customer-operated installs must provide `--object-storage-verification`.
- secret manager read: a configured secret reference can be read without
  exposing the secret value in output. Cloud, production, and
  customer-operated installs must provide `--secret-manager-verification`.
- OpenAI-compatible Model Gateway health: `/readyz` proves the model gateway is
  configured, and cloud, production, and customer-operated installs must also provide a
  redacted `--model-gateway-verification` result from a live
  OpenAI-compatible planning request that returns the expected
  `planning.record` verification tool before acceptance. The evidence must
  match `/readyz.checks.model_gateway`: direct providers compare `base_url` and
  `model`, while provider-registry installs require the evidence `provider_id`
  to be one of the configured provider IDs.
- sandbox health: a redacted sandbox lifecycle verification result proves the configured sandbox provider can expose controller capabilities, declare network/filesystem/runtime isolation, resource limits, image-policy enforcement with allowed runtime images, create a session, execute an artifact-producing command, list and download the generated artifact, reject cross-workspace/run command, file-write, file-read, and snapshot probes, destroy the session, block post-destroy command execution, and reject unauthenticated tenant session-list, global session-list, and `/capabilities` probes when a controller API key is configured. Production and customer-operated validation also rejects evidence whose provider does not match `/readyz.checks.sandbox.provider` and rejects packaged/default `TAROAI_SANDBOX_CONTROLLER_API_KEY` values before accepting sandbox evidence.
- browser-controller health: when browser execution is enabled, the deployment config includes `TAROAI_BROWSER_CONTROLLER_BASE_URL`, `/readyz.checks.browser` reports `capabilities_checked=true` after the API reads the controller `/capabilities` response, the configured browser controller returns `/healthz`, and a redacted browser-controller lifecycle verification result proves the controller exposes `/capabilities`, declares session TTL and capacity limits, can open a session, reject duplicate session creation, enforce workspace/run session-read, session-delete, and action scope, execute an action, verify a screenshot or extract response, delete the browser session, confirm the deleted session is no longer readable, and reject unauthenticated tenant session-list, global session-list, and `/capabilities` probes when a controller API key is configured. Cloud, production, and customer-operated validation treats missing browser-controller capabilities or lifecycle evidence as failed acceptance when `/readyz.checks.browser.configured=true` and rejects evidence whose provider does not match `/readyz.checks.browser.provider`. Production and customer-operated deployments must set `TAROAI_BROWSER_CONTROLLER_API_KEY` and reject packaged/default browser-controller keys before probing `/healthz`.
- Web Workspace health: when a customer-facing workspace is packaged, `--web-base-url`
  returns the web workspace HTML and `assets/main.js`, including the chat
  column, login controls, composer controls, readiness strip,
  browser/artifact surfaces, Bearer auth, `/readyz` preflight, and storage
  download contract.
- API health: `/healthz` and `/readyz` return healthy responses.
- sandbox readiness: `/readyz.checks.sandbox.configured` is `true` for production and customer-operated deployments, with `controller_required=true`, `controller_configured=true`, `controller_endpoint_configured=true`, `controller_auth_configured=true`, `capabilities_checked=true`, runtime isolation, image-policy enforcement with `allowed_image_count > 0`, network/filesystem isolation, resource limits, destroy support, TTL enforcement, capacity limits, and no missing fields for `k8s` or `e2b`. If `/readyz` reports `sandbox_controller_capabilities` as missing or reports weak controller capability declarations, the install is not accepted until the API can authenticate to the sandbox controller and read a sufficient `/capabilities` response.
- browser readiness: `/readyz.checks.browser.configured` is `true` for enabled browser-controller deployments only after the API confirms endpoint/auth settings and reads controller `/capabilities`, reporting auth, TTL, global/tenant/run capacity, and navigation allowlist declarations. If `/readyz` reports `browser_controller_capabilities` as missing or reports weak auth, TTL, or capacity declarations, the install is not accepted until the API can authenticate to the browser controller and read a sufficient `/capabilities` response.
- event stream: a run event stream can be opened and receives an event id.
  Cloud, production, and customer-operated installs must provide
  `--event-stream-verification`.
- worker queue: a job can be enqueued, claimed, acknowledged, and observed in
  queue metrics. Cloud, production, and customer-operated installs must provide
  `--redis-queue-verification`.
- audit write: an audit event can be written and read back for the current
  tenant. Cloud, production, and customer-operated installs must provide
  `--audit-write-verification`.
- trace collector: the configured OTLP HTTP collector accepts a verification
  span without exposing collector credentials in output.
  Cloud, production, and customer-operated installs must provide
  `--trace-collector-verification`.
- support bundle redaction: a redaction evidence report proves support bundles
  can be sanitized before leaving the customer boundary. Production and
  customer-operated installs must provide
  `--support-bundle-redaction-evidence`.
- backup restore drill: a customer-approved restore drill proves backup manifest,
  restore order, restored dependencies, and post-restore validation.
  Cloud, production, and customer-operated installs must provide
  `--restore-drill-verification`.
- runtime closed loop: a redacted demo gate report proves the strict execution
  path reached the Workspace, Runtime, sandbox command, storage-backed
  artifact, event stream, trace, and browser-controller governance gates.
  Cloud, production, and customer-operated installs must provide
  `--runtime-closed-loop-evidence`. The report must have passed
  `demo_ready`, `workspace_execution_ready`, `skill_reuse_ready`, and
  `browser_controller_governance_ready`; production and customer-operated
  installs must also pass `sandbox_governance_ready`. `skill_reuse_ready`
  proves that a solution-pack/skill reuse path created a run, promoted an
  artifact, exposed safe terminal evidence, and remained selectable from recent
  run history.

If a deployment intentionally exposes only API services, omit `--web-base-url`
and the Web Workspace health check is reported as skipped. Customer demo and
employee-facing packages should provide the web URL so the validator proves the
entrypoint is reachable before acceptance.

customer-operated deployments must not use `local_process` as the sandbox provider.
The Settings profile gate rejects `local_process`, `docker`, and `disabled`
sandbox providers for BYOC, VPC, private, and air-gapped modes before install
validation starts. Use a customer-approved isolated provider such as Kubernetes,
E2B, or a microVM-backed execution service for shared employee command execution.
The current executable provider gate accepts `k8s` and `e2b`, with air-gapped
mode still rejecting external E2B. Accepted enterprise sandbox providers must
also configure `TAROAI_SANDBOX_CONTROLLER_BASE_URL` and a generated
`TAROAI_SANDBOX_CONTROLLER_API_KEY` in the runtime secret. API and worker
processes use that HTTP controller endpoint and bearer key for sandbox
lifecycle, command, file write/read, snapshot, and destroy operations. The lifecycle
evidence provider must match `/readyz.checks.sandbox.provider` after treating
`k8s` and `kubernetes` as the same provider, so a customer install cannot pass
with evidence collected from a different sandbox backend.
Install validation also checks the sandbox lifecycle evidence provider for
production and customer-operated modes, and rejects evidence generated from
`local_process` or `docker` even if the lifecycle smoke actions themselves
succeeded. Local and Docker evidence remain useful for PoC debugging, but they
are not customer acceptance evidence for shared employee execution.
Air-gapped install validation is stricter: sandbox lifecycle evidence must come
from the internal Kubernetes sandbox controller path, not E2B, because external
execution services are outside the air-gapped boundary.
The controller response is part of the isolation boundary: session, command,
file write/read, and snapshot responses must echo the requested tenant, workspace, run,
session, and path identifiers wherever those identifiers apply. The API rejects
mismatched sandbox controller responses instead of accepting cross-tenant
session state or promoting artifacts from the wrong run.

Production environments must not use `local_process` even in managed-cloud mode.
The Settings profile gate rejects `local_process`, `docker`, and `disabled`
sandbox providers when `TAROAI_ENVIRONMENT` is `production` or `prod`; use the
local cloud PoC template only for local validation. Production profiles must also
configure `TAROAI_SANDBOX_CONTROLLER_BASE_URL` before startup and should pass
`TAROAI_SANDBOX_CONTROLLER_API_KEY` through the approved secret store. The
install validator should fail the API readiness check when
`/readyz.checks.sandbox.configured` is not `true`.
For Kubernetes-backed sandbox execution, operators must retain evidence that the
target namespace applies restricted Pod Security Admission labels, sandbox-controller
and browser-controller Pods run with read-only root filesystems plus explicit
writable `emptyDir` mounts for `/tmp` and runtime work directories, sandbox Pod
`ResourceQuota`, container `LimitRange` defaults, and a namespace-level
default-deny `NetworkPolicy` for sandbox session Pods before accepting install
validation. The provider evidence must also prove the sandbox-controller
`Role` matches the least-privilege pod, pod exec, and NetworkPolicy rules and
that the `RoleBinding` binds only the configured controller `ServiceAccount`
to that `Role`. It also records the sandbox runner `ServiceAccount`, rejects
evidence where runner token automount is not explicitly disabled, and fails
acceptance when the verified sandbox session ran outside the runtime-policy
namespace, used any ServiceAccount other than that runner, or reused the
controller ServiceAccount. The raw
manifests provide this in
`infra/k8s/sandbox-runtime-policy.yaml` and `infra/k8s/sandbox-controller.yaml`;
the Helm chart exposes equivalent controls through `sandboxRuntimePolicy.enabled`,
`sandboxRuntimePolicy.namespaceLabels`, `sandboxRuntimePolicy.resourceQuota`,
`sandboxRuntimePolicy.limitRange`, and `sandboxRuntimePolicy.networkPolicy`.
Adjust quota and limit values to the approved node pool capacity and record the
applied values with the sandbox lifecycle evidence.

Production and customer-operated deployments must use durable backend settings.
The Settings profile gate rejects the in-memory defaults for control-plane,
identity, connector, skill, solution-pack, SSO, SCIM, knowledge, long-term
memory, trigger, storage-catalog, lifecycle, and model-policy stores, and also
requires Redis for short-term memory and job queues, before install validation
starts.

Production and customer-operated deployments must not enable dev request headers.
The Settings profile gate rejects `TAROAI_DEV_REQUEST_HEADERS_ENABLED=true` when
`TAROAI_ENVIRONMENT` is `production` or `prod`, and also rejects it for BYOC,
VPC, private, and air-gapped modes. Use Bearer tokens, SSO, or another approved
enterprise authentication path for install validation.

Production and customer-operated deployments must not use default authentication
secrets. The Settings profile gate rejects the built-in `access_token_secret`
and `password_hash_salt` defaults, including local cloud PoC values, for
`prod`/`production` and customer-operated modes. It also requires
`TAROAI_ACCESS_TOKEN_SECRET`, `TAROAI_PASSWORD_HASH_SALT`, and configured
`TAROAI_EXTERNAL_SHARE_LINK_TOKEN_HASH_SECRET` values to be at least 32
characters, and requires `TAROAI_PASSWORD_HASH_ITERATIONS` to be at least
`600000`. Generate unique deployment values and store them in the approved
secret manager before install validation.

Production and customer-operated deployments must not use local or placeholder
operator tokens. The Settings profile gate rejects local bootstrap and sandbox
resolver token placeholders, browser-controller placeholders, and configured
operator tokens shorter than 32 characters; leave the token empty to disable
that bootstrap/resolver path, or configure a generated deployment-specific
value in the approved secret manager. The install validator also reads
`TAROAI_SANDBOX_CONTROLLER_API_KEY` and `TAROAI_BROWSER_CONTROLLER_API_KEY`
from the environment, or accepts them through `--sandbox-controller-api-key`
and `--browser-controller-api-key`, and fails production/customer-operated
reports when either value is still one of the packaged local defaults.

Production and customer-operated deployments that enable `TAROAI_BROWSER_PROVIDER`
must configure `TAROAI_BROWSER_CONTROLLER_BASE_URL` and a generated
`TAROAI_BROWSER_CONTROLLER_API_KEY`. The Settings profile gate rejects a missing
endpoint, an empty key, and the packaged `replace-with-browser-controller-key`
placeholder before install validation starts, so browser session/action routes
cannot be deployed without a reachable controller and bearer auth. The
browser-controller service also rejects configured API keys shorter than 32
characters. `/readyz.checks.browser` reports provider, controller endpoint,
controller auth, missing fields, and configured state so `scripts/validate-install.sh`
can skip a deliberately disabled browser provider or fail an enabled provider
before attempting `/healthz`. Cloud, production, and customer-operated
acceptance fails when `/readyz` omits `checks.browser`, because the validator
cannot distinguish a disabled browser provider from a stale API readiness
contract.
When `/readyz.checks.browser.configured=true` for a cloud, production, or
customer-operated install, `scripts/validate-install.sh` now treats
`--browser-controller-verification` as required acceptance evidence rather than
an optional smoke check. `/healthz` only proves the service answers; the
verification result proves session open, duplicate rejection, scoped action
rejection, list/action/capture-or-extract/delete behavior under tenant scope.

Production and customer-operated deployments must not use local secret
management. The Settings profile gate rejects
`TAROAI_DEPLOYMENT_SECRET_MANAGER_TYPE=local` and
`TAROAI_SECRET_SERVICE_BACKEND=memory` when `TAROAI_ENVIRONMENT` is
`production` or `prod`, and also rejects those local settings for BYOC, VPC,
private, and air-gapped modes. Configure a durable external backend such as AWS
Secrets Manager for provider credentials, connector tokens, and customer-owned
API keys before running install validation.

## Expected Report

The validator should emit JSON compatible with `InstallValidationReport`:

```json
{
  "deployment_id": "private-acme",
  "deployment_mode": "private",
  "checked_at": "2026-01-01T00:00:00Z",
  "status": "passed",
  "checks": [
    {
      "name": "database_migration",
      "status": "passed",
      "dependency": "database",
      "message": "database migration validated"
    }
  ]
}
```

Failed checks must include a dependency-specific remediation:

```json
{
  "name": "object_storage_read_write",
  "status": "failed",
  "dependency": "object_storage",
  "message": "upload denied",
  "remediation": "check S3 credentials and bucket policy"
}
```

## Validation Command

Run the helper from the repository root or packaged release directory:

```bash
scripts/validate-install.sh \
  --mode private \
  --web-base-url "${TAROAI_WEB_BASE_URL}" \
  --sandbox-controller-api-key "${TAROAI_SANDBOX_CONTROLLER_API_KEY}" \
  --browser-controller-api-key "${TAROAI_BROWSER_CONTROLLER_API_KEY}" \
  --sandbox-verification sandbox-verification.json \
  --kubernetes-sandbox-verification kubernetes-sandbox-verification.json \
  --output install-validation.json
```

Generate and retain a database migration plan after the migration job runs:

```bash
scripts/build-migration-plan.sh \
  --database-url "${TAROAI_DATABASE_URL}" \
  --migrations-path apps/api/migrations \
  > migration-plan.json
```

Run the object storage verifier from the same network boundary as the API or
operator host, and retain its JSON output. The output records signed URL
methods only, not the raw signed URLs; install validation rejects object storage
evidence that includes unexpected fields such as raw signed URLs.

```bash
scripts/verify-object-storage.sh \
  --endpoint-url "${TAROAI_OBJECT_STORAGE_ENDPOINT}" \
  --bucket "${TAROAI_OBJECT_STORAGE_BUCKET}" \
  --region "${TAROAI_OBJECT_STORAGE_REGION:-us-east-1}" \
  --access-key-id "${TAROAI_OBJECT_STORAGE_ACCESS_KEY_ID}" \
  --secret-access-key "${TAROAI_OBJECT_STORAGE_SECRET_ACCESS_KEY}" \
  > object-storage-verification.json
```

Run the Redis queue verifier against the same Redis database used by workers,
and retain its JSON output. The result never includes the raw Redis URL; install
validation rejects Redis queue evidence that contains unexpected fields such as
connection strings.

```bash
scripts/verify-redis-queue.sh \
  --redis-url "${TAROAI_REDIS_URL}" \
  > redis-queue-verification.json
```

Run the secret manager verifier from the same trust boundary as the API or
operator host, and retain its redacted JSON output. The wrapper calls
`python -m taroai.secrets.verification` with the repo Python path. It creates a
temporary scoped verification secret, issues a short-lived lease, resolves the
lease from the bound run/step/session context, verifies that an out-of-scope
context is denied, confirms the evidence output is redacted, and deletes the
created verification secret when the backend supports cleanup:

```bash
scripts/verify-secret-manager.sh \
  --backend "${TAROAI_SECRET_SERVICE_BACKEND}" \
  --region-name "${TAROAI_AWS_REGION:-}" \
  --endpoint-url "${TAROAI_SECRET_SERVICE_ENDPOINT_URL:-}" \
  --secret-name-prefix "${TAROAI_SECRET_SERVICE_NAME_PREFIX:-taroai/validation}" \
  --kms-key-id "${TAROAI_SECRET_SERVICE_KMS_KEY_ID:-}" \
  --secret-value-env-var TAROAI_SECRET_MANAGER_VERIFICATION_VALUE \
  > secret-manager-verification.json
```

Run the authenticated event stream verifier with a tenant user that can create
and read a validation run. The wrapper calls
`python -m taroai.deployment.api_verification --check event_stream` with the
repo Python path. Retain its redacted JSON output, which confirms that the
stream opened, an SSE id was received, replay by `after_sequence` and
`Last-Event-ID` worked, tenant scope was enforced, and payload safety checks
passed. The verifier treats generic sensitive response patterns such as Bearer
headers, credentialed HTTP URLs, signed URLs, connection strings, and sensitive
JSON fields as unsafe payload evidence:

```bash
scripts/verify-event-stream.sh \
  --api-base-url "${TAROAI_API_BASE_URL}" \
  --access-token-env-var TAROAI_INSTALL_VERIFY_ACCESS_TOKEN \
  --denied-access-token-env-var TAROAI_INSTALL_VERIFY_DENIED_ACCESS_TOKEN \
  --workspace-id "${TAROAI_INSTALL_VERIFY_WORKSPACE_ID}" \
  > event-stream-verification.json
```

To bind event evidence to the strict Workspace-to-artifact acceptance run, pass
that source verifier run as `--run-id` instead of letting the verifier create a
new run. For example:

```bash
scripts/verify-event-stream.sh \
  --api-base-url "${TAROAI_API_BASE_URL}" \
  --access-token-env-var TAROAI_INSTALL_VERIFY_ACCESS_TOKEN \
  --denied-access-token-env-var TAROAI_INSTALL_VERIFY_DENIED_ACCESS_TOKEN \
  --workspace-id "${TAROAI_INSTALL_VERIFY_WORKSPACE_ID}" \
  --run-id "$(jq -r '.run_id' dist/local-cloud-poc-strict-e2e-result.json)" \
  > event-stream-verification.json
```

The event-stream evidence includes only non-sensitive traceability fields such
as `api_base_url`, `run_id`, and `first_event_sequence`; it must not include
the run prompt, access token, raw event payload beyond the verifier schema, or
tenant data from the denied scope.
Cloud, production, and customer-operated install validation rejects legacy event-stream
evidence that omits any of `api_base_url`, `run_id`, or
`first_event_sequence`, even when the boolean replay checks are true. It also
rejects event-stream evidence whose `api_base_url` does not match the
`--api-base-url` used for install validation, so reconnect evidence cannot be
reused from a different API environment. When audit-write evidence is supplied
in the same install validation run, both evidence files must also carry the same
`run_id`.

For the local strict Compose gate, setting
`TAROAI_COMPOSE_STRICT_E2E_INSTALL_VALIDATION_OUTPUT` makes
`scripts/verify-compose-strict-e2e.sh` derive this run id from
`dist/local-cloud-poc-strict-e2e-result.json`, generate event-stream and
audit-write evidence for that same run, generate sandbox lifecycle and
browser-controller evidence from the Compose controllers, generate model
gateway, object-storage, Redis queue, and migration-plan evidence from the same
local stack, build/sign/verify a local release package transfer evidence file,
build and redact a small support bundle, and pass those files into
`scripts/validate-install.sh` alongside the runtime closed-loop demo gate. The
host-side model verifier cannot read a runtime-only
`TAROAI_MODEL_GATEWAY_API_KEY_SECRET_REF_ID`; this bridge therefore requires a
direct `TAROAI_MODEL_GATEWAY_API_KEY` or `TAROAI_MODEL_GATEWAY_PROVIDERS` value
that includes verifier-readable credentials. Provider JSON that uses
`api_key_secret_ref_id` must also provide
`TAROAI_MODEL_GATEWAY_VERIFICATION_SECRET_VALUES` or
`TAROAI_MODEL_GATEWAY_VERIFICATION_SECRET_VALUE_ENV_JSON`, otherwise the bridge
fails before starting Docker Compose. The
same bridge also accepts pre-generated external evidence through
`TAROAI_COMPOSE_STRICT_E2E_SECRET_MANAGER_VERIFICATION`,
`TAROAI_COMPOSE_STRICT_E2E_TRACE_COLLECTOR_VERIFICATION`, and
`TAROAI_COMPOSE_STRICT_E2E_RESTORE_DRILL_VERIFICATION`; each supplied path must
exist before it is forwarded to install validation.

Run the authenticated audit write verifier with a tenant user that can create a
validation run and read audit events. The wrapper calls
`python -m taroai.deployment.api_verification --check audit_write` with the repo
Python path. Retain its redacted JSON output, which confirms write, read-back,
tenant scope, and sensitive metadata redaction:

```bash
scripts/verify-audit-write.sh \
  --api-base-url "${TAROAI_API_BASE_URL}" \
  --access-token-env-var TAROAI_INSTALL_VERIFY_ACCESS_TOKEN \
  --denied-access-token-env-var TAROAI_INSTALL_VERIFY_DENIED_ACCESS_TOKEN \
  --workspace-id "${TAROAI_INSTALL_VERIFY_WORKSPACE_ID}" \
  > audit-write-verification.json
```

To bind audit evidence to the strict acceptance run, pass the same `--run-id`
used for event-stream verification:

```bash
scripts/verify-audit-write.sh \
  --api-base-url "${TAROAI_API_BASE_URL}" \
  --access-token-env-var TAROAI_INSTALL_VERIFY_ACCESS_TOKEN \
  --denied-access-token-env-var TAROAI_INSTALL_VERIFY_DENIED_ACCESS_TOKEN \
  --workspace-id "${TAROAI_INSTALL_VERIFY_WORKSPACE_ID}" \
  --run-id "$(jq -r '.run_id' dist/local-cloud-poc-strict-e2e-result.json)" \
  > audit-write-verification.json
```

The audit-write evidence includes only non-sensitive traceability fields such
as `api_base_url` and `run_id`; it must not include the run prompt, access
token, raw audit metadata beyond the verifier schema, or tenant data from the
denied scope. The audit verifier applies the same generic sensitive-response
pattern check before marking metadata redaction as confirmed.
Cloud, production, and customer-operated install validation rejects legacy audit-write
evidence that omits either `api_base_url` or `run_id`, even when write and
read-back checks are true. It also rejects audit-write evidence whose
`api_base_url` does not match the `--api-base-url` used for install validation,
so audit evidence cannot be reused from a different API environment. When
event-stream evidence is supplied, the audit `run_id` must match the event
stream `run_id`, proving both checks observed the same validation run.

Run the OTLP HTTP trace collector verifier from the same network boundary as
the API or worker process, and retain its redacted JSON output. The wrapper
calls `python -m taroai.observability.verification` with the repo Python path:

```bash
scripts/verify-trace-collector.sh \
  --endpoint-url "${TAROAI_TRACE_EXPORTER_ENDPOINT_URL}" \
  --api-key "${TAROAI_TRACE_EXPORTER_API_KEY}" \
  --service-name "${TAROAI_TRACE_EXPORTER_SERVICE_NAME:-taroai-api}" \
  --deployment-environment "${TAROAI_ENVIRONMENT:-private}" \
  > trace-collector-verification.json
```

The verifier sends one `trace.collector.verify` span through the same OTLP HTTP
exporter used by runtime trace export. The result records only endpoint,
span-count, resource/scope span-count, whether an authorization header was
sent, and `secret_value_exposed=false`; it must not include the collector API
key.

Run the backup restore drill evidence builder from the restore environment after
the database migration plan, object storage verifier, and Redis queue verifier
have been captured. The wrapper calls
`python -m taroai.deployment.restore_drill_verification` with the repo Python
path. The builder emits the redacted JSON consumed by
`--restore-drill-verification`; the restore drill lifecycle API also validates
run-record evidence objects against this same JSON schema before accepting
`evidence_ready`, requires the storage object content type to be
`application/json`, rejects retention-expired evidence objects, and requires
every restore verification check in the evidence to pass:

```bash
scripts/verify-restore-drill.sh \
  --drill-id restore_drill_2026_07 \
  --backup-manifest backup-manifest.json \
  --executed-restore-order database,object_storage,redis,config,workers \
  --migration-plan migration-plan.json \
  --object-storage-verification object-storage-verification.json \
  --redis-queue-verification redis-queue-verification.json \
  --config-restored \
  --post-restore-checks-passed \
  --rpo-minutes 45 \
  --rto-minutes 25 > restore-drill-verification.json
```

For deployments without Redis in the backup manifest, omit
`--redis-queue-verification` and use the manifest restore order without
`redis`. Retain the resulting JSON, which confirms the backup manifest was
generated, restore order was executed, database/object storage/Redis or rebuild
path/config restoration were verified, and post-restore validation passed:

```json
{
  "drill_id": "restore_drill_2026_07",
  "backup_manifest_generated": true,
  "restore_order_executed": true,
  "database_restore_verified": true,
  "object_storage_restore_verified": true,
  "redis_restore_or_rebuild_verified": true,
  "config_restore_verified": true,
  "post_restore_validation_passed": true,
  "rpo_minutes": 45,
```

contract: workspace and `/tmp` `emptyDir.sizeLimit` values must be present and
match the requested ephemeral-storage limit, `activeDeadlineSeconds` must be

are missing from the verification schema or show a weaker Pod/container policy.

base images such as `python:3.12-slim` are local verification inputs rather than
customer install acceptance evidence. The packaged sandbox-controller rejects
empty Kubernetes allowed-image lists, broad catch-all patterns, and wildcard tag

Workspace demo instead of accepting a command-only smoke check.

cluster credentials; install validation rejects unexpected provider evidence
fields.

`GET /capabilities`, and requires all three to return `401` or `403`. The verifier
requires the authenticated capabilities response to declare
`network_isolation=true`, `filesystem_isolation=true`, `resource_limits=true`,

`runtime_isolation=true`, `image_policy_enforced=true`,
`allowed_image_count > 0`, a non-empty `max_session_ttl_seconds`, a non-empty `max_sessions`, a non-empty

command execution, and destroy succeed.

When the packaged controller is configured with
`TAROAI_SANDBOX_CONTROLLER_PROVIDER=kubernetes`, capture provider-level cluster
evidence before the HTTP lifecycle evidence:

```bash
scripts/verify-kubernetes-sandbox.sh \
  --namespace taroai \
  --service-account-name taroai-sandbox-runner \
  --runtime-class-name gvisor \
  --runtime-class-required \

```

This verifier exercises the underlying kubectl-backed provider directly: it
creates the sandbox Pod and deny-all NetworkPolicy, uploads an input file,
executes a command, downloads the generated artifact, records a snapshot URI,
and destroys the Pod plus NetworkPolicy. The provider also enforces configured
image patterns, must require a non-empty runtime class for install acceptance,
and exposes orphaned Pod cleanup
for sandbox sessions no longer tracked by the controller. Leave
`TAROAI_SANDBOX_CONTROLLER_KUBERNETES_ORPHAN_CLEANUP_ENABLED=false` until the
operator has confirmed the controller's active-session set is authoritative for
the namespace. When enabled, cleanup deletes session Pods that are no longer
active or have expired and confirms each deleted Pod is no longer active and
each per-session NetworkPolicy is gone before reporting the cleanup result.
After controller restart, the Kubernetes provider rebuilds that active-session
view from sandbox Pod labels, annotations, and the live per-session NetworkPolicy
before session list, capacity, TTL, and follow-up session lookup for
command/file/snapshot checks. With
`--verify-runtime-policy`, the same JSON also records
namespace Pod Security labels, sandbox runtime hard quota, `LimitRange`
container defaults/max values, the default-deny runtime `NetworkPolicy`, and
the sandbox-controller `Role`/`RoleBinding` least-privilege check plus the
sandbox-runner ServiceAccount token-automount setting. Install validation also
checks that the verified sandbox session Pod ran in that same namespace, used
that same runner ServiceAccount, and did not run as the controller
ServiceAccount; it also rejects evidence where the per-session NetworkPolicy
does not target the verified sandbox session, does not cover both Ingress and
Egress, or includes allow rules instead of deny-all behavior. Keep this JSON
alongside install validation evidence for customer-operated clusters.
Expired tracked sessions are rejected before any workspace command/file/snapshot
operation and the provider issues `kubectl delete` for the session Pod and
per-session NetworkPolicy, then confirms the Pod is no longer active before
confirming the NetworkPolicy is gone and marking the session destroyed locally.
Configure standalone controller limits with
`TAROAI_SANDBOX_CONTROLLER_SESSION_TTL_SECONDS`,
`TAROAI_SANDBOX_CONTROLLER_MAX_SESSIONS`,
`TAROAI_SANDBOX_CONTROLLER_MAX_SESSIONS_PER_TENANT`, and
`TAROAI_SANDBOX_CONTROLLER_MAX_SESSIONS_PER_RUN`.
The API also checks the same capabilities before opening HTTP-controller-backed
sandbox sessions, so a controller that loses an isolation or resource-limit
capability, stops enforcing session TTL, or stops declaring session capacity is
rejected before `/sessions` is called. Requests whose `timeout_seconds` exceeds
`max_session_ttl_seconds`, or whose visible tenant/run active session counts
have reached capacity, are rejected by the API before session creation; global
session capacity is enforced by the sandbox controller service itself.
The controller must also serve `GET /sessions?tenant_id=...` with a
tenant-scoped session list. The API and Agent Runtime use that list for
sandbox concurrency and
license enforcement before creating another controller-backed
sandbox session, including sessions opened automatically for `sandbox.command`
steps. Taroai rejects listed sessions whose tenant does not match the query.
`POST /sessions` must return the created session with `status=active`; a
successful response that returns a destroyed or inactive session is rejected
before tool execution starts. `GET /capabilities` and `POST /sessions` must also
identify the configured provider, with `k8s` and `kubernetes` treated as aliases.
`DELETE /sessions/{session_id}?tenant_id=...&workspace_id=...&run_id=...` must return the destroyed session
with `status=destroyed`; a 200 response that leaves the session active is
treated as a sandbox provider failure. After destroy, the verifier sends a
same-scope command probe and records `post_destroy_command_blocked=true`; install
validation fails if that destroyed session can still execute commands.
The lifecycle verifier now requires the created session to appear in the
allowed tenant's session list and to remain absent from the denied tenant's
session list, so install evidence proves both concurrency visibility and
tenant-scoped listing.
It also submits command, file-write, file-read, and snapshot probes with the same
tenant/session but a different workspace/run, and requires those operations to
fail with scoped not-found or forbidden semantics before the evidence can pass.
The file-read probe is recorded as `file_read_scope_enforced`.
This prevents a controller from accepting a valid session ID as authority for
another workspace or run.
